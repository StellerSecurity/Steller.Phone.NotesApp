STELLAR NOTES ENCRYPTED BACKUP — FORMAT 1

Scope: encrypted exported file at rest. This does not redesign the installed
app's V1 storage, make an unlocked/rooted/compromised device safe, or guarantee
forensic erasure from RAM, flash journals, caches or existing copies.

Key: 30 independently and uniformly generated decimal digits (~99.66 bits),
from the operating system CSPRNG through Web Crypto. Rejection sampling removes
modulo bias. Leading zeroes are significant. Spaces/hyphens may group entry.
No user-selected short PIN, account password, device code, or app code is reused.
The code must be re-entered before export, kept separately, and is never stored,
logged, sent to the server or put in the backup file. No automatic clipboard copy.
Lost code means the backup cannot be recovered by Stellar.

Crypto: existing locked libsodium-wrappers-sumo 0.8.2 / libsodium-sumo 0.8.2.
No new dependency or installation. Argon2id 1.3, opslimit 3, memlimit 268435456
bytes (256 MiB), salt 16 random bytes, derived key 32 bytes. XChaCha20-Poly1305
IETF AEAD, fresh 24-byte nonce and 16-byte authentication tag. No silent weaker
fallback on memory allocation or platform failure.

JSON outer envelope (UTF-8, .stellarbackup):
format=stellar-notes-backup, version=1, kdf=argon2id13, memlimit=268435456,
opslimit=3, cipher=xchacha20poly1305-ietf, salt, nonce, ciphertext.
Salt/nonce/ciphertext use standard padded Base64. Canonical AAD is the compact
JSON serialization of these fields in the listed order, excluding ciphertext.
The entire ordinary stellar-notes-export v1 document is the AEAD plaintext,
including titles, folders, HTML/images embedded in HTML, Trash metadata and
individually locked-note ciphertext. No root key, session or account credentials.

Import rejects unsupported costs/version, excessive sizes, wrong codes, damaged
or truncated files before altering notes. KDF costs are fixed and validated
before derivation; hostile files cannot request arbitrarily large RAM/CPU costs.
Maximum plaintext 32 MiB, input envelope 48 MiB, 10000 notes/folders each.
Crypto runs in a dedicated local worker with no network calls. Buffers containing
password/key/plaintext are wiped where possible before returning; the worker is
terminated after each operation or cancellation. JS/OS memory erasure is not
claimed. A strong encrypted file does not protect against capture of its code.

Import requires file plus code, then a count-only preview and confirmation.
Preview stays in memory and expires after two minutes or app lock/session change.
Imported notes receive new UUIDs; matching active folder names are reused without
changing existing notes. Individual note locks remain intact. Existing notes are
never replaced; file identifiers cannot overwrite an account's synced notes.
Rendering uses the existing shared Quill/sanitization rules. Failure preserves
original notes, with a rollback attempt if local persistence fails. Local success
is separate from later network synchronization.

The normal app exposes only encrypted backup and import. The native writer
rejects plaintext note documents and accepts only the authenticated encrypted
container. The ordinary JSON schema exists only inside the encrypted payload.
Previous user-created files are not removed. The existing consent countdown,
device-code gate and fresh app-code check remain required.
